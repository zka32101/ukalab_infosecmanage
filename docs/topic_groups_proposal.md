# 分野の細分化 提案(topicId の分野グループ化)

> **これは提案ドキュメントです(コード・データの変更は含みません)。**
> 本アプリは非公式の学習アプリで、試験実施団体とは無関係です。以下の「分野グループ」は、アプリ内で問題を探しやすくするために **本アプリが独自に付けた区分** であり、公式の出題区分・シラバスの分類ではありません(名称・並びも公式資料に準拠していません)。画面上でも「公式の分類ではありません」の旨を小さく添える前提です。

- 作成日: 2026-10-20
- 対象データ: `assets/questions/info_security.jsonl`(1,042問)、`assets/questions/info_security_multi_angle.jsonl`(72問)、`assets/terms/info_security.jsonl`(318語)、`assets/exam/info_security.json`、`assets/experience/reading_info_security.jsonl`
- 確認日時点の件数(main の最新データから再集計)

## 0. 背景と現状

現状の科目は 2 つだけ。

|---|---|---:|
| kamoku_a | 科目A(知識) | 754 |

- 各問題は `topicId`(26種)を持つ。A は 16 種、B は `case_` 付き 10 種(A と B で topicId が重ならない)。

- アプリの画面(解く / 記録 / 模擬試験 / 用語 / 読み物)は **すべて `subjectId` 単位** で動いている。`topicId` は履歴・弱点集計の内部キーとして保存されているが、画面の分類には使われていない。
- `docs/syllabus_mapping.md` の件数(833問など)は古い。本書の件数が最新。

## 2. UI案

前提: どの案でも、分野グループは **アプリ側の対応表**(`topicId → groupId`、約 26 行)で表現できる。問題データの `subjectId` / `topicId` は変えない。

### 2-1. 「解く」タブでの分野選択

- 画面上部に「科目 / 分野」の切り替え。分野を選ぶとグループ一覧(名前・問題数・解答済み割合)を表示し、タップでそのグループの出題を開始。
- グループ内に「知識 / 事例 / すべて」のチップ(科目をまたぐ案の場合)。
- 実装はアプリ側のみで可能: 出題プールを「グループに属する topicId の問題」で絞り込んでから、既存の出題セッションに渡す。
- 一覧の末尾に「公式の分類ではありません」の小さな注記。

### 2-2. 記録画面の分野別正答率・解答済み割合

- 現在は科目別(`computeSubjectProgress`)のみ。同じ計算を `groupId` 単位に差し替えた「分野別」セクションを追加する。
- 表示項目: グループ名、解答済み / 問題数(割合バー)、正答率。解答数が少ないグループは「データ不足」と表示して極端な値を出さない。
- 履歴は `topicId` を保存済みのため、**過去の解答も新しい分野グループで遡って集計できる**(データ移行不要)。
- 弱点(正答率が低い分野)から「この分野を解く」への導線を置く。

### 2-3. カスタム模擬試験での分野絞り込み

- コアの `CustomMockExamSetupScreen` は `SubjectConfig` のリスト(ID と名前)を受け取り、選ばれた ID を返す。**グループを `SubjectConfig(subjectId: groupId, name: グループ名)` として渡せば、コアを変えずに複数選択 UI を流用できる**。
- 選ばれたグループの `topicId` に属する問題で出題プールを絞ったうえで、既存の `pickCustomMockExamQuestions` に渡す(科目 ID は全科目を指定)。
- 「科目A/B」と「分野」の両方で絞りたい場合は、アプリ側で独自の設定画面を作る(コア変更なしでも可能。コア変更なら共通部品化できる)。
- 本番形式の模擬試験(48 + 12)は科目単位のまま変更しない。

### 2-4. 用語集の分野対応

- 用語(318語)は `topicId` を持たない。`relatedQuestionIds` から導く:
  1. 用語に紐づく問題の `topicId` を集計し、最頻の `topicId` → グループを「主分野」とする。
  2. 複数のグループに紐づく用語は、副分野としても表示(絞り込みでは両方にヒット)。
- 実データでの試算(案2、主分野で割り当て): 攻撃と技術的対策 88 / 法令・規格・社内ルール 54 / ネットワークとIT基礎 44 / 組織の管理と監査 35 / 開発・クラウド・リモート 32 / 基礎とリスク 28 / インシデント対応 16 / 人と場所の対策 10 / **紐づけなし 11**。
- 318語のうち 121語(約 38%)は複数の topicId の問題に紐づいている。主分野だけで割り当てると偏るので「副分野もヒット」方式が安全。
- 紐づけなしの 11 語は「その他」に入れる(将来 `relatedQuestionIds` を補うか、用語に分野を直接持たせる)。
- 用語の `subjectId` は現在 kamoku_a/b だが、事例の分野(case_*)に紐づく用語は事例の問題経由で導かれる。

### 2-5. 読み物を分野単位にする案の比較

現状の読み物(`ChapterReading`)は科目ごと 2 本(`reading-kamoku_a` に 3 節、`reading-kamoku_b` に 2 節)だけで、`subjectId` を必須とする。コアの `ChapterReading` に分野を表すフィールドはない。

| 案 | 内容 | スキーマ変更 | コア変更 | 長所 | 短所 |
|---|---|---|---|---|---|
| R-a | **1科目に複数レコード**: `readingId` を `reading-kamoku_a-<groupId>` のように分け、`subjectId` は kamoku_a のまま、`title` に分野名を入れる。分野との対応はアプリ側の対応表(readingId → groupId)で持つ | なし | なし | すぐ始められる。コア更新に依存しない | readingId の命名規則で対応を表すため、対応表の保守が要る。`subjectId` が分野を表さない |
| R-b | コアの `ChapterReading` に `groupId`(任意の文字列)フィールドを追加し、JSON に `"groupId"` を書く | あり(任意項目) | **あり** | データだけで分野対応が完結。他のうかラボアプリも使える | コアのリリース → アプリのコア ref 更新が必要。検証ツール(`validate_content`)の対応も要確認 |
| R-c | 読み物の `relatedQuestionIds` から分野を導く(用語と同じ方式) | なし | なし | 追加の対応表が不要 | 読み物ごとに関連問題を正しく並べる作業が要る。1 本が複数分野にまたがりやすい |

推奨: **まず R-a**(コア変更なし)で分野別読み物を作り、運用して必要になれば R-b を検討する。いずれの案でも、読み物の本文は **自作の解説**(試験実施団体の資料の転載をしない)という既存方針を維持する。

## 3. 実装の順序案(コア変更の有無)

| 段階 | 内容 | コア変更 | 目安 |
|---|---|---|---|
| 1 | 分野グループ対応表(`topicId → groupId`・表示名・並び)をアプリ内に追加。単体テストで「26 種すべてが 1 グループに属する」を保証(topicId が増えたらテストが落ちる) | なし | 小 |
| 2 | 記録画面に分野別正答率・解答済み割合を追加(履歴の `topicId` を利用) | なし | 小〜中 |
| 3 | 「解く」タブに分野選択を追加(プールを絞って既存セッションに渡す) | なし | 中 |
| 4 | カスタム模擬試験の分野絞り込み(グループを `SubjectConfig` として渡す方式) | なし | 小 |
| 5 | 用語集の分野絞り込み(`relatedQuestionIds` から導出) | なし | 小〜中 |
| 6 | 読み物の分野別化(案R-a) | なし(R-b を選ぶ場合のみあり) | 中(文章作成が主) |
| 7(任意) | 他のうかラボアプリでも使うなら、対応表の仕組み・分野別の集計・絞り込み UI をコアへ移す | **あり** | 大 |

**段階 1〜6 はコア変更なしで実現できる**。コアに移すのは、別アプリでも同じ仕組みを使うと決まってからで十分。

### 採用しない方針とその理由

- **`subjectId` を分野グループに置き換える**(`exam/info_security.json` の subjects をグループにする):画面は変更が少なく済むが、(1) 本番形式の模擬試験の配分(`subjectQuestionCounts`: 48 / 12)と合否ルール、(2) 全国集計の `examVersion`、(3) 過去の履歴・進捗(`subjectId` キー)、(4) 問題データ全 1,114 行の書き換えとコンテンツ検証の整合、のすべてに影響する。移行コストとリスクが大きいため非推奨。
- **`topicId` そのものを書き換える**: 履歴・弱点集計の既存キーが変わり、過去の解答との対応が崩れる。非推奨。

### 注意点

- 追加形式(○×等、72 問)は `kNewQuestionTypesEnabled` フラグが false の間は出題されない。分野別の問題数表示は、フラグの状態に応じて「出題に使える問題」で数える(基本セットと追加形式を混ぜない)。
- 分野グループは **非公式** であることを、画面とストア説明の双方で矛盾しない表現にそろえる。
- 問題・用語が増えたとき、`topicId` が新設されたら対応表への追加を忘れないよう、テストで検知する(上記段階 1)。

## 4. オーナーに決めてほしい点

1. **粒度**: 案1(12グループ)と案2(8グループ)のどちらにするか。または「案2 で始め、大きいグループだけ後で分割」とするか。
2. **科目との関係**: 分野が科目をまたぐ(案1・案2)か、科目内で分ける(案2')か。またぐ場合、グループ内の「知識 / 事例」絞り込みを置くか。
3. **グループ名**: 仮名のままでよいか、言い換えたい語はあるか(語調を平易にするか、固い名称にするか)。
4. **mgmt(62問)の扱い**: 雑多な分野のため、案1 では「ISMSと管理運営」(183問)に入れて大きくなっている。分割(例: 運用管理 / 事業継続・委託)や、一部問題の topicId 見直しをするか。
5. **it_basics(36問)の置き場**: 「ネットワークとIT基礎」に束ねてよいか、独立させるか。
6. **「公式分類ではない」注記の文言と表示場所**(分野一覧の下、設定画面、ストア説明のどこに出すか)。
7. **画面の入口**: 「解く」タブの既定を科目 / 分野のどちらにするか。分野を既定にする場合、科目別の入口を残すか。
8. **用語集**: 複数分野に紐づく用語を「副分野もヒット」方式にしてよいか。紐づけなしの 11 語の扱い(「その他」/ 問題への紐づけを補う)。
9. **読み物**: 分野別に増やすか(増やす場合は案R-a / R-b のどちらか、まず作る分野の優先順位)。
10. **追加形式(72問)**: 分野別の問題数表示に含めるか(フラグが有効になるまで含めない案を推奨)。
11. **コアへの移管**: 他のうかラボアプリにも展開する予定があるか(あれば段階 7 を前倒し検討)。
12. **進め方**: 段階 1〜6 のうち、最初のリリースに入れる範囲(推奨: 1 + 2 + 3)。
